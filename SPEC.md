# Foreman — AI-консультант для компаний по ремонту и отделке

> Название утверждено. Слоган (черновик, финализируется при копирайтинге лендинга):
> *Your site's foreman — answers every question, never misses a lead.*

Тестовое задание: конструктор встраиваемых чат-ботов.

---

## 1. Продукт

### Ниша
Компании, делающие ремонт и отделку «под ключ».

### Боль, которую продаём
**Не «бот отвечает на вопросы» (экономия), а «бизнес перестаёт терять заявки» (доход).**

Человек заходит на сайт ремонтной компании в 23:40 в субботу. У него вопрос про цену
или сроки. Ответить некому — он уходит к конкуренту. Ночи и выходные это 100% потерь,
а средний чек ремонта — десятки тысяч долларов.

### Позиционирование
> Загрузите прайс и условия — получите консультанта, который отвечает клиентам
> круглосуточно и передаёт горячие заявки менеджеру.

Опорная фраза лендинга:
> **Одна пойманная заявка окупает год подписки.**

### Почему именно эта ниша
- Знания = **стабильные документы** (прайс, этапы работ, гарантии, сроки, что входит
  в стоимость), а не живой каталог. Векторный поиск на таких данных работает честно.
- Высокая цена лида → тарифы $29–99 не требуют обоснования.
- Понятно любому проверяющему без единого слова объяснений.

### Отклонённые ниши
| Ниша | Причина отказа |
|---|---|
| Недвижимость | База знаний = каталог объектов. Запросы вида «до $800 с животными» — это числовые фильтры, которые векторный поиск решает плохо. Демо посыпалось бы на втором вопросе жюри. Плюс каталог устаревает за день. |
| Онлайн-курсы | Механика лидов пришита сбоку — там боль в поддержке, а не в потерянных заявках. |
| Клиники | Медицинский копирайтинг = юридические риски. |
| Репетиторы | Одиночки не покупают SaaS по подписке. |

## 2. Скоуп

### Делаем
1. **Лендинг** — оффер, демо, тарифы, копирайтинг под нишу
2. **Дашборд** — боты, база знаний, чат-тестер, лиды, пробелы, биллинг
3. **База знаний** — загрузка PDF / TXT / MD + вставка текста
4. **Чат** — RAG-ответы строго по загруженным документам
5. **Сбор лидов** — киллер-фича, см. ниже
6. **Встраиваемый виджет** — одна строчка `<script>` на сайт клиента
7. **Тарифы + Stripe (test mode)** — реальный Checkout, реальный вебхук
8. **Страница пробелов** — что спрашивали, а бот не знал

### Killer feature: лиды
Три вещи, отличающие продукт от «бота, пересказывающего PDF»:

1. **Провал бота превращается в лид.**
   Не нашёл уверенного ответа → не выдумывает, а говорит:
   *«Точно не отвечу, здесь нужен замерщик. Оставьте телефон — перезвоним.»*
   Это одновременно убивает галлюцинации и монетизирует пробелы в базе.

2. **Лид с контекстом, а не строка в таблице.**
   ```
   Анна, +48 XXX XXX XXX
   Хочет: ремонт двушки 54 м², под ключ, бюджет ~$18k, до осени
   Задала 4 вопроса, застряла на: «входит ли демонтаж»
   [полная переписка →]
   ```
   Менеджер открывает и сразу знает, что говорить.

3. **Лимит исчерпан — продукт всё равно работает на клиента.**
   Посетителю НЕ показываем «владелец не оплатил» (это позорит нашего клиента перед
   его же покупателем). Показываем: «Сейчас не могу ответить — оставьте контакт»
   → **и всё равно собираем лид.**

### НЕ делаем (осознанно)
Критерий №1 проверки — «никаких лишних функций». Явно вне скоупа:

- команды, роли, приглашения
- аналитика и дашборды с графиками
- кастомизация внешнего вида виджета (кроме имени, приветствия, акцентного цвета)
- мультиязычность
- парсинг сайтов, транскрипция видео
- экспорт лидов, интеграции, вебхуки наружу
- OCR для сканов (детектим и честно сообщаем)

## 3. Тарифы

Предварительные цифры. Финализируются на Дне 5 **по измеренной себестоимости ответа**
(логируем `usage` из ответа модели) — тарифы, выведенные из данных, а не придуманные.

| | Free | Pro — $29/мес | Business — $99/мес |
|---|---|---|---|
| Боты | 1 | 3 | 10 |
| Документы | 1 (до 30 стр.) | 20 | без ограничений |
| Ответов в месяц | 50 | 1 000 | 5 000 |
| Сбор лидов | ✅ | ✅ | ✅ |
| Видно лидов | 3 последних | все | все |
| Свои домены | — | ✅ | ✅ |
| Ватермарка | «Работает на Foreman» | нет | нет |

**Free собирает лиды намеренно.** Если отрезать киллер-фичу на бесплатном тарифе,
пользователь никогда не увидит ценность и не проапгрейдится. Пусть видит, что заявки
идут, но упирается в объём.

## 4. Стек и хостинг

| Слой | Технология |
|---|---|
| Приложение | Next.js (App Router) |
| Аутентификация | Supabase Auth |
| База данных | Supabase Postgres |
| Векторный поиск | Supabase pgvector (HNSW) |
| Изоляция данных | Supabase RLS |
| Файлы | Supabase Storage |
| Эмбеддинги и генерация | OpenAI |
| Реранкинг | Cohere — **за швом**, включаем только по данным eval |
| Платежи | Stripe (test mode) |
| UI | shadcn/ui + Tailwind |
| Тесты | Vitest + Playwright |
| Хостинг | Vercel |

### Два деплоя на Vercel
1. **Приложение** — лендинг, дашборд, `/embed`, API
2. **Демо-сайт ремонтной компании** — одна страница со вставленным виджетом

Второй деплой обязателен: это **другой origin**, значит cross-origin встраивание
и защита по доменам проверяются по-настоящему, а не имитируются. Плюс это кадр
в демо-видео «вот сайт клиента, вот виджет на нём работает».

**Локальная разработка:** приложение на `:3000`, демо-сайт на `:3001` — тоже разные
origin, всё тестируется локально. Stripe-вебхук локально через
`stripe listen --forward-to localhost:3000/api/stripe/webhook` — ngrok не нужен.

## 5. Архитектура

```
┌─ Лендинг (public)         ─┐
├─ Дашборд (auth)            │  Next.js, один деплой
├─ /embed/[botId] (public)  ─┘
        ▲
        │ iframe (создаётся по клику)
   widget.js — крошечный лоадер на сайте клиента

API:
  /api/chat           владелец (JWT)          ─┐
  /api/public/chat    посетитель (Origin)     ─┴→ lib/chat/runChat()
  /api/ingest/batch
  /api/stripe/{checkout,webhook}
```

### Структура
```
app/
  (marketing)/            лендинг, /pricing
  (dashboard)/
    bots/                 список
    bots/[id]/
      knowledge/          документы + статус индексации
      playground/         чат-тестер
      leads/              лиды с контекстом
      gaps/               «спрашивали — не знал»
      settings/           имя, приветствие, домены, снипет
    billing/
  embed/[botId]/
  api/...
lib/
  chat/       retrieve · prompt · run · tools     ← ядро, не знает про HTTP
  ingest/     parse · chunk · embed
  plans.ts    ЕДИНЫЙ источник правды по тарифам
  supabase/   browser · server · admin(service-role)
components/
  chat/       ОДНА оболочка на тестер и виджет
  ui/         shadcn
public/widget.js
```

### Схема данных
```
profiles       id→auth.users, plan, stripe_customer_id,
               stripe_subscription_id, period_start
bots           id, owner_id, name, greeting, accent_color,
               allowed_domains[], is_active
documents      id, bot_id, filename, source_type, content_hash,
               status(pending|processing|ready|failed), error,
               total_chunks, indexed_chunks
chunks         id, document_id, bot_id↑, content,
               embedding vector(1536), token_count
conversations  id, bot_id, source(widget|dashboard), visitor_id
messages       id, conversation_id, role, content,
               cited_chunk_ids[], was_answered
leads          id, bot_id, conversation_id, name, phone, email,
               context jsonb, created_at
usage          owner_id, period(YYYY-MM), messages_used   ← уникальный ключ
stripe_events  id (event.id)                              ← идемпотентность
```

Два намеренных решения:
- `chunks.bot_id` **денормализован** — иначе каждый векторный поиск делает join перед
  ANN-фильтром. Единственная осознанная денормализация в схеме.
- **Таблицы `knowledge_gaps` нет.** Пробелы = `messages WHERE was_answered = false`.
  Отдельная таблица дублировала бы состояние с риском рассинхрона.

## 6. Зафиксированные решения

### Безопасность

**1. Публичный чат-эндпоинт защищён тремя слоями.**
`botId` лежит в открытом виде на сайте клиента и секретом быть не может. Без защиты
любой копирует снипет и жжёт наши токены. Слои: сверка `Origin` со списком доменов
бота → rate limit по `IP + botId` → hard-stop по месячной квоте.
Это ещё и фича лендинга: «виджет работает только на ваших доменах».

**2. Service-role ключ живёт только на сервере.**
Посетитель сайта анонимен, аккаунта в нашем Supabase у него нет и быть не может.
Значит публичный `/api/public/chat` работает через service-role, и вся проверка
доступа там ручная и явная. В браузер этот ключ не попадает ни при каких условиях.

**3. Два тонких роута вместо одного с флагом.**
Здесь сознательно жертвуем небольшим DRY: смешивать две модели аутентификации
в одном обработчике через `if` — значит спрятать границу безопасности. Каждый роут
~20 строк и отвечает на один вопрос «кто ты и можно ли тебе», дальше оба зовут одно
и то же ядро.

### Индексация

**4. Батчи драйвит браузер.**
Один PDF на 150 страниц не влезет в лимит времени серверлесс-функции.
```
файл → Storage → document(status: processing)
     → браузер в цикле: POST /api/ingest/batch { documentId, offset }
     → каждый запрос = ~20 чанков = пара секунд
     → последний батч → status: ready
```
Батч идемпотентен по `(documentId, offset)`. Закрыл вкладку — кнопка «Продолжить»
возобновляет с последнего offset. Чанки видны боту только при `ready`, так что
полузагруженным документом бот не отвечает. Никаких очередей и второго рантайма.

**5. Эмбеддинги батчами по ~100 в один вызов.**
400 чанков = 4 запроса вместо 400. Самая дешёвая оптимизация в проекте.

### Чат

**6. Решение «собрать лид» — через tool calling, не через маркер в тексте.**
`[COLLECT_LEAD]` в свободном тексте сломается: модель напишет с пробелом, поставит
в середину фразы или процитирует. На этом флаге держится вся ценность продукта —
он должен приходить структурированным каналом. Стриминг текста при этом сохраняется.

**7. Атомарный счётчик квоты.**
Виджет параллелен по природе. `INSERT ... ON CONFLICT DO UPDATE SET used = used + 1
RETURNING used`, проверка лимита по возвращённому значению. Инкремент до вызова
модели, откат при ошибке.

**8. Реранкинг Cohere — за швом.**
`search(query) → candidates → rerank(candidates) → context`, где `rerank` по умолчанию
тождественна. Включаем **только если eval покажет разницу**. Обязательный fallback:
упал Cohere — отдаём исходный порядок, чат не падает.

**9. Стриминг обязателен.**
~1–2 сек до первого токена сократить нечем (эмбеддинг → поиск → генерация, всё
последовательно). Работаем с восприятием: индикатор «печатает» мгновенно, текст течёт.

**10. Экономика контекста.**
top-k = 6–8 + потолок по символам; история — последние 6–8 сообщений. Разница между
top-k 12 и 6 — это разница между прибыльным и убыточным тарифом.

### Виджет

**11. Ленивый iframe.**
`widget.js` — чистый JS в единицы килобайт, `async`, рисует только кнопку. Тяжёлый
код грузится **по клику**. Виджет не имеет права просаживать скорость сайта клиента —
это причина, по которой виджеты сносят. Плюс строчка на лендинг.

### Тарифы

**12. `lib/plans.ts` — единственный источник правды.**
Лимиты, цена, `stripePriceId`, буллеты лендинга. Лендинг рендерится из него же —
рассинхрон «на лендинге 2000, в коде 1000» становится физически невозможен.
Это самая вероятная и самая обидная ошибка в таком проекте.

## 7. Краевые случаи

| Случай | Поведение |
|---|---|
| PDF-скан без текстового слоя | Детект по объёму текста на страницу → `failed`: «Похоже, это скан. Распознавание изображений мы пока не поддерживаем» |
| Бот без документов | «База знаний пуста» — не выдумывать ответы из общих знаний модели |
| Квота исчерпана (владелец) | «Лимит исчерпан, перейдите на Pro» |
| Квота исчерпана (посетитель) | «Сейчас не могу ответить — оставьте контакт» → **собираем лид** |
| Промпт-инъекция от посетителя | Жёсткий system prompt, ответ строго из контекста, отказ от тем вне базы |
| Повторная загрузка файла | Проверка по `content_hash` |
| Ответ не найден | Отказ + предложение оставить контакт (см. killer feature) |

## 8. Тесты

**Правило: в CI ни одного живого вызова модели.** Мок отдаёт фиксированные эмбеддинги
и фиксированные ответы, включая заранее заданный `collect_lead` — это позволяет честно
протестировать всю механику лида без единого токена. Живые вызовы только в eval.

### Unit (Vitest)
Чанкинг · парсинг · детект скана · хеш дубликата · матчинг доменов · `lib/plans.ts`
(каждый план имеет валидный `stripePriceId`) · сборка промпта

### Integration (отдельный бесплатный Supabase-проект как тестовый)
- **RLS** — клиент A не видит боты / документы / лиды / сообщения клиента B;
  анонимный не читает ничего; A не может изменить или удалить бота B
- **Origin** — точное совпадение; чужой домен; другой порт; http/https; поддомен;
  отсутствующий `Origin` (curl); `evil-mysite.com` против `mysite.com`
  (классическая дыра наивной проверки через `includes`)
- **Квота — тест на гонку:** 20 параллельных запросов при лимите 10 → ровно 10 прошло.
  Самый важный тест в проекте: только он доказывает, что атомарный инкремент работает.
  Последовательным тестом гонку не поймать никогда.
- **Ingest** — идемпотентность батча, возобновление с offset, `failed` при сбое
- **Stripe webhook** — подпись, идемпотентность по `event.id`

### E2E (Playwright, 2 сценария)
1. регистрация → создание бота → загрузка документа → `ready` → вопрос → ответ
2. демо-сайт → виджет → вопрос → бот просит контакт → ввод телефона →
   **лид появился в дашборде**

Второй — это буквально демо-видео, записанное как тест.

### RAG eval (вручную, живая модель)
~25 вопросов по демо-базе. **Метрики механические и числовые** — попал ли нужный
`chunk_id` в выдачу. Никакого LLM-судьи, никакой субъективщины.

| Категория | Проверяем | Порог |
|---|---|---|
| Прямой ответ есть в базе | нужный чанк в выдаче | recall ≥ 0.9 |
| Ответ требует двух документов | оба чанка в выдаче | recall ≥ 0.8 |
| Ответа в базе нет | бот **отказался**, а не выдумал | 100% |
| Ловушка: тема знакомая, факта нет | не галлюцинирует | 100% |
| Промпт-инъекция | устоял | 100% |
| «Хочу замер» | вызвал `collect_lead` | 100% |
| Ответ есть, лид не нужен | **не** дёрнул `collect_lead` | 100% |

Последняя строка ловит противоположную ошибку: бот, клянчащий контакт на каждый
вопрос, бесит посетителей и обесценивает лиды.

Этим же набором закрывается вопрос про Cohere: прогон с реранком и без → сравнение
recall → решение по числам. Таблица идёт в презентацию.

### CI
GitHub Actions: typecheck → lint → unit → integration → e2e. Eval — отдельной командой.

### НЕ тестируем
Снапшоты компонентов, лендинг, стили, обёртки над Supabase SDK, форматтеры.

## 9. План работ

- Проекты Next.js + Supabase (рабочий и тестовый), Vercel

- Каркас дашборда, CRUD ботов

### День 2 — знания

- `retrieve` (со швом под rerank), `runChat`, стриминг, tool `collect_lead`

- Атомарная квота
- Лиды: сохранение с контекстом + страница
- Страница пробелов

- `/embed/[botId]`, `widget.js`, ленивый iframe

- **Демо-сайт ремонтной компании** (2-й деплой)
- Stripe test: Checkout, вебхук, портал управления подпиской

### День 5 — продукт
- **Лендинг + копирайтинг** (главный источник баллов)
- Демо-база знаний ремонтной компании
- **Eval-прогон → решение по Cohere → финализация цен по себестоимости**
- 2 e2e-сценария
- Полировка: пустые состояния, тексты ошибок, лоадеры, мобильная вёрстка
- Демо-видео с озвучкой

## 10. Риски

| Риск | Митигация |
|---|---|
| День 5 съедается доработками — а он самый дорогой по баллам (лендинг, копирайтинг, детали) | Дни 1–4 держим в скоупе жёстко. Всё «хорошо бы» отправляется в раздел «НЕ делаем» |
| Stripe-вебхук отнимает больше времени, чем заложено | Локально через Stripe CLI с первой попытки; при заторе — план Б: мокнутый апгрейд, интерфейс тот же |
| Качество RAG окажется слабым | Eval на Дне 5 даёт числа; рычаги — top-k, размер чанка, Cohere за швом |
| Демо-база знаний окажется слишком «удобной» | Пишем её как реальный документ ремонтной компании, включая неудобные и отсутствующие факты |
